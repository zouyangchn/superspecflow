# Businessbook — 团队业务域规范基准

> 本文件是团队级业务域规范的**权威基准**。当 superspecflow skill 为项目生成 `openspec/specs/business-domain.md` 时，必须以此为基线框架，再叠加从项目代码和业务文档中提取的特有业务信息。
>
> **说明**：与 codebook.md 和 architecturebook.md 不同，业务域规范高度依赖具体项目，本文件主要提供**结构框架和通用原则**，具体内容以项目实际情况为准。

---

## 一、基准文件结构指引

子项目的 `business-domain.md` 应至少包含以下章节，按此结构组织：

```markdown
# business-domain.md — <项目名>

## 核心业务概念与术语
## 主要功能模块
## 业务流程说明
## 数据模型概要
## 接口与业务映射
## 业务规则与约束
## 项目特有业务知识   ← 此节由项目分析生成，基准文件中不覆盖具体内容
```

---

## 二、核心业务概念与术语

### 2.1 编写原则

**2.1.1** 【强制】业务术语必须统一。同一概念在不同子系统之间不允许有不同的命名。

**2.1.2** 【强制】每个核心业务概念必须有清晰的定义，包括：名称（中英文）、业务含义、数据载体（对应哪些表/字段）、状态流转（如有）。

**2.1.3** 【推荐】建立术语表，列出所有业务术语及其定义，作为团队沟通的统一词典。

### 2.2 示例结构

```markdown
### <业务概念名>（<英文名>）

- **业务含义：** <一句话描述该概念在业务中的角色>
- **数据载体：** <对应的数据库表/字段>
- **状态流转：** <如有，列出所有状态及转换条件>
- **关联概念：** <与哪些其他业务概念有关联>
```

---

## 三、主要功能模块

### 3.1 编写原则

**3.1.1** 【强制】功能模块划分必须清晰明确，每个模块有独立的职责边界。

**3.1.2** 【强制】模块间的依赖关系必须明确，标注数据流向和调用方向。

**3.1.3** 【推荐】使用模块依赖图辅助说明。

### 3.2 示例结构

```markdown
### <模块名>

- **职责：** <该模块的核心职责>
- **入口：** <用户/系统如何访问该模块>
- **依赖：** <该模块依赖哪些其他模块>
- **被依赖：** <哪些模块依赖该模块>
```

---

## 四、业务流程说明

### 4.1 编写原则

**4.1.1** 【强制】核心业务流程必须有完整的流程描述，覆盖正常流程和异常分支。

**4.1.2** 【强制】如果业务对象状态超过 3 个，必须使用状态图表达，明确每个状态转换的触发条件。

**4.1.3** 【强制】端到端时效：全部工作流流程时效需支持端对端计算方式（如复核提交从 A 到 B 到 C），整体时效可追踪。

**4.1.4** 【推荐】调用链路涉及对象超过 3 个时，使用时序图。

### 4.2 示例结构

```markdown
### <业务流程名>

- **触发条件：** <什么情况下触发该流程>
- **参与角色：** <哪些角色参与>
- **正常流程：**
  1. <步骤1>
  2. <步骤2>
  3. ...
- **异常分支：**
  - <异常场景1> → <处理方式>
  - <异常场景2> → <处理方式>
- **时效要求：** <端到端时效指标>
```

## 五、数据模型概要

### 5.1 编写原则

**5.1.1** 【强制】核心业务表之间的关系必须清晰记录（一对一、一对多、多对多）。

**5.1.2** 【强制】码表与基础表的关系必须明确。码表 `pub_` 开头只能由配置管理系统维护，基础表 `t_cfg_`/`f_cfg_` 同步后不可修改。

**5.1.3** 【强制】禁止大宽表设计，表的拆分要合理。

**5.1.4** 【推荐】核心业务表的字段含义应有简要说明，特别是状态字段和枚举字段。

### 5.2 示例结构

```markdown
### 核心表关系

| 主表 | 关联表 | 关系 | 关联字段 | 说明 |
|------|--------|------|----------|------|
| t_xxx_main | t_xxx_detail | 一对多 | main_id | 主表-明细 |
| t_xxx_main | pub_status | 多对一 | status_code | 状态码表 |

### 核心业务表

#### <表名>

| 字段 | 类型 | 含义 |
|------|------|------|
| ... | ... | ... |
```

## 六、接口与业务映射

### 6.1 编写原则

**6.1.1** 【强制】对外暴露的接口必须与业务场景对应，记录每个接口服务的业务场景。

**6.1.2** 【强制】接口设计必须满足幂等性。

**6.1.3** 【强制】对外接口需明确加密加签，不允许明文对接。

**6.1.4** 【强制】同步接口需有降级措施，不允许中断关键业务流程。

### 6.2 示例结构

```markdown
### <接口名>

- **URL：** <接口路径>
- **业务场景：** <该接口服务的业务场景>
- **幂等策略：** <唯一请求ID / 状态机校验 / 数据库唯一约束>
- **超时设置：** <连接超时/读超时>
- **降级策略：** <返回默认值 / 使用缓存 / 异步补偿>
```

---

## 七、业务规则与约束

### 7.1 编写原则

**7.1.1** 【强制】关键业务规则必须文档化，避免只存在于代码中。

**7.1.2** 【强制】批量操作的业务规则需要特别标注：导入功能是否有类型选项、权限设置、文件大小限制；批量查询/批量算是否经过评审。

**7.1.3** 【强制】定时任务和补偿功能的重复次数管控规则必须记录。

**7.1.4** 【推荐】业务规则变更时应同步更新本文档。

### 7.2 通用业务约束（团队级）

以下约束适用于所有项目的业务开发：

**7.2.1** 【强制】表单提交前后端必须防重点击：前端 disable + 后端 Redis KEY 管控。

**7.2.2** 【推荐】导出功能：大清单用单独服务；同一用户同时只能一个导出作业；耗时长的用异步。

**7.2.3** 【强制】第三方数据推送必须客户信息脱敏加密。

**7.2.4** 【推荐】新系统原则上不存在跨库（租户/用户）场景，抄单应有服务化实现方式。

**7.2.5** 【强制】非关键流程避免同步调用，不能影响关键流程。

**7.2.6** 【强制】配置表变更需走审批流程，由配置管理系统统一处理。
