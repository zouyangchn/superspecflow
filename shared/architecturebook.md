# Architecturebook — 团队架构规范基准

> 本文件是团队级架构规范的**权威基准**。当 superspecflow skill 为项目生成 `openspec/specs/architecture.md` 时，必须以此为基线，再叠加从项目代码中提取的特有架构信息。
>
> **约束力说明**：【强制】必须遵守；【推荐】建议遵守，特殊情况可灵活处理；【参考】视场景选择性采纳。

---

## 一、基准文件结构指引

子项目的 `architecture.md` 应至少包含以下章节，按此结构组织：

```markdown
# architecture.md — <项目名>

## 技术栈
## 目录结构
## 模块结构与依赖关系
## 应用分层规范
## 构建配置（构建工具、启动命令、构建命令）
## 路由架构（前端）/ 中间件配置（后端）
## HTTP 通信方案
## 数据库规范
## 中间件使用规范
## 接口设计规范
## 日志与监控设计
## 安全设计
## 环境配置
## 项目特有架构约定   ← 此节由项目分析生成
```

---

## 二、技术栈

**2.1** 【强制】方案必须符合项目声明的技术栈，不得引入规范文件中未声明的新依赖。

**2.2** 【强制】线上应用不要依赖 SNAPSHOT 版本（安全包除外）。

**2.3** 【推荐】底层基础技术框架、核心数据管理平台、近硬件端系统谨慎引入第三方实现。

---

## 三、目录结构与模块关系

**3.1** 【强制】存储方案和底层数据结构的设计必须获得评审一致通过，并沉淀为文档。评审内容包括存储介质选型、表结构设计、存取性能、字段关系等。

**3.2** 【强制】类在设计与实现时要符合单一职责原则。

**3.3** 【推荐】谨慎使用继承，优先使用聚合/组合方式。

**3.4** 【推荐】根据依赖倒置原则尽量依赖抽象类与接口。

**3.5** 【推荐】对扩展开放，对修改关闭。共性业务抽取为公共模块，不出现重复代码。

---

## 四、应用分层规范

### 4.1 分层结构

后端代码调用顺序严格遵守：`Controller → Service → Mapper`。

| 层级 | 职责 |
|------|------|
| 开放接口层 | 封装 Service 方法暴露为 RPC/HTTP 接口 |
| Web 层（Controller） | 访问控制、参数校验、简单转发，不写业务逻辑 |
| Service 层 | 具体业务逻辑实现 |
| Manager 层 | 通用业务处理（第三方封装、通用能力下沉、多 DAO 组合） |
| DAO 层（Mapper） | 数据访问，与数据库交互 |

**4.1.1** 【强制】Controller 层只写入口，所有业务逻辑在 Service 层。

**4.1.2** 【强制】事务管控在 Service 层，不允许在 Controller 层。

**4.1.3** 【强制】禁止在 Service 层从 Session 获取登录用户信息。Controller 获取后通过参数传递。

**4.1.4** 【强制】禁止在 Service 层拼接 SQL。

**4.1.5** 【强制】Service 与 Mapper 注解注入时，变量名为类型首字母小写，不允许简写。

**4.1.6** 【强制】单表 Mapper 只允许本表数据操作方法。单表 Service 只允许调用本表 Mapper。

### 4.2 分层异常处理

| 层级 | 处理方式 |
|------|----------|
| DAO 层 | `catch(Exception)` + `throw new DAOException(e)`，不打印日志 |
| Service 层 | 必须记录出错日志到磁盘，带上参数信息 |
| Controller 层 | 不继续上抛，跳转友好错误页面 |
| 开放接口层 | 转化为错误码和错误信息返回 |

### 4.3 领域模型

| 模型 | 说明 |
|------|------|
| DO | 与数据库表结构一一对应，DAO 层向上传输 |
| DTO | 数据传输对象，Service/Manager 向外传输 |
| BO | 业务对象，Service 层输出的封装业务逻辑 |
| Query | 数据查询对象，超过 2 个参数的查询封装，禁止用 Map |
| VO | 显示层对象，Web 向模板渲染引擎传输 |

## 五、构建配置

**5.1** 【强制】GAV 命名规则：

| 项 | 格式 |
|----|------|
| GroupID | `com.{公司/BU}.业务线[.子业务线]`（最多 4 级） |
| ArtifactID | `产品线名-模块名` |
| Version | `主版本号.次版本号.修订号`（起始 1.0.0） |

**5.2** 【强制】二方库新增或升级，保持除功能点外的 jar 包仲裁结果不变。

**5.3** 【强制】依赖同一二方库群时定义统一版本变量。

**5.4** 【强制】禁止子项目 pom 中出现相同 GroupId + ArtifactId 但不同 Version。

**5.5** 【推荐】依赖声明放 `<dependencies>`，版本仲裁放 `<dependencyManagement>`。

## 六、接口设计规范

**6.1** 【强制】接口设计必须满足幂等性原则。

**6.2** 【强制】接口超时时间设计时明确：HTTP 连 5 秒读 10 秒；Dubbo 5 秒内。

**6.3** 【强制】接口设计要考虑事务补偿原则。

**6.4** 【强制】对外暴露的查询接口必须加密加签，不允许明文对接。

**6.5** 【强制】同步接口要有降级措施，不允许中断关键业务流程。

**6.6** 【强制】非关键流程避免同步调用，不影响关键流程。

**6.7** 【强制】同步服务不允许调用第三方批查、批算操作。

**6.8** 【强制】第三方数据推送必须脱敏加密。

**6.9** 【强制】接口入参和出参必须用 DTO 对象封装，禁止使用 Map。

**6.10** 【强制】端到端时效：工作流全流程需支持端对端计算，每个环节记录开始和结束时间。

**6.11** 【推荐】接口响应体统一结构：

```java
public class Result<T> {
    private String code;
    private String message;
    private T data;
    private boolean success;
}
```

**6.12** 【推荐】接口版本管理用 URL 路径方式（`/api/v1/xxx`）。

## 七、数据库规范

### 7.1 建表规范

**7.1.1** 【强制】所有新建表必须包含标配字段：

```sql
valid_ind     VARCHAR(2)    NOT NULL   COMMENT '有效标识，1-有效，0-无效',
remark        VARCHAR(2000) DEFAULT NULL COMMENT '备注',
flag          VARCHAR(2)    DEFAULT NULL COMMENT '预留字段',
created_by    VARCHAR(60)   NOT NULL   COMMENT '创建者',
date_created  DATETIME      NOT NULL   COMMENT '创建时间',
updated_by    VARCHAR(60)   NOT NULL   COMMENT '修改者',
date_updated  DATETIME      NOT NULL   COMMENT '修改时间'
```

**7.1.2** 【强制】表名、字段名小写字母或数字，禁止数字开头，禁止两个下划线间只有数字。

**7.1.3** 【强制】表名不使用复数名词。禁用保留字。

**7.1.4** 【强制】小数类型用 `decimal`，禁止 `float` 和 `double`。

**7.1.5** 【强制】`varchar` 不超过 5000，超过用 `text` 独立建表。

**7.1.6** 【强制】禁止自增主键，用雪花算法分布式 ID。

**7.1.7** 【强制】表之间 E-R 关系清晰，不做大宽表，合理拆分，适当冗余。

**7.1.8** 【强制】数据库脚本文件（DDL/DML/PCK）必须 UTF-8 无 BOM。

### 7.2 命名规范

| 表类型 | 命名规则 | 示例 |
|--------|----------|------|
| 码表 | `pub_` 开头 | `pub_sex` |
| 基础表 | `t_cfg_`（源系统）/ `f_cfg_`（同步系统） | `t_cfg_company` |
| 业务表 | `t_业务系统简码_` | `t_ply_quotation_main`、`t_clm_regist_main` |

**7.2.1** 【强制】码表只能由配置管理系统增删改，同步服务同步，业务系统不可直接修改。

**7.2.2** 【强制】禁止通用码表（如 pubcode）。

### 7.3 索引规范

**7.3.1** 【强制】索引命名：`idx_表名_字段名`（≤30 字符）。主键 `pk_`，唯一索引 `uk_`。

**7.3.2** 【强制】业务唯一字段必须建唯一索引。

**7.3.3** 【强制】超过三个业务表禁止 join（关联码表和基础表除外）。

**7.3.4** 【推荐】单表非主键索引不超过 5 个；单字段不超过 4 个索引；组合索引不超过 3 字段。

**7.3.5** 【推荐】索引选查询频率高、区分度高的字段。组合索引最常用的放前面。

**7.3.6** 【强制】建索引需走审批流程。

### 7.4 SQL 规范

**7.4.1** 【强制】用 `count(*)` 不用 `count(列名)`。

**7.4.2** 【强制】用 `ISNULL()` 判断 NULL。`sum()` 注意 NPE，用 `IFNULL(SUM(col), 0)`。

**7.4.3** 【强制】禁止外键与级联，在应用层解决。

**7.4.4** 【强制】禁止存储过程。

**7.4.5** 【强制】数据订正先 SELECT 确认再执行。

**7.4.6** 【强制】多表操作列名前加表别名限定。

**7.4.7** 【强制】查询不使用 `*`，明确写出字段。

**7.4.8** 【推荐】`in` 操作控制在 1000 个以内。

### 7.5 查询规范

**7.5.1** 【强制】禁止模糊多表关联查询，分通道拆分 SQL 为精确查询。

**7.5.2** 【强制】各系统有自身综合查询功能，封装细粒度服务。精确查询与批量查询分流。

**7.5.3** 【强制】字典表码表从 Redis 缓存取代码和名称转化。

**7.5.4** 【强制】页面搜索禁止左模糊/全模糊，走搜索引擎。

### 7.6 大数据平台约束

**7.6.1** 【强制】Hive/Impala 分区表查询必须含分区过滤条件。

**7.6.2** 【强制】Hive/Impala 禁止 UPDATE/INSERT/DELETE。

**7.6.3** 【强制】StarRocks 禁止创建外表。

**7.6.4** 【推荐】StarRocks 尽量不用 `count(distinct)`。

## 八、中间件使用规范

### 8.1 Redis

| 序号 | 规范 |
|------|------|
| 1 | Key 命名用项目名或简称做前缀，不含特殊字符 |
| 2 | 生产禁止 FLUSHALL/FLUSHDB/KEYS/DEBUG/MSET |
| 3 | 不建议 SCAN，数据量 < 1 万用 Hash/Set，量大用 DB |
| 4 | 选用本科室/业务线专用 Redis |
| 5 | String < 10KB；Hash/List/Set/ZSet 元素 < 5000 |
| 6 | 非字符串 bigkey 用渐进式删除或 unlink，禁止 del |
| 7 | 数据必须设置过期时间 |
| 8 | 不推荐 Redis 事务 |
| 9 | 连接数三级：8-4-1（默认）、16-8-1（需运维）、32-10-2（需架构） |

### 8.2 RabbitMQ

| 序号 | 规范 |
|------|------|
| 1 | 必须使用 Virtualhost + 独立账号 |
| 2 | 每系统两个账号：`系统名_user` + `系统名_admin` |
| 3 | Exchange 以 `ex_` 开头 |
| 4 | 高可用队列以 `ha.` 开头 |
| 5 | Virtualhost 以 `/` 开头接系统名 |
| 6 | Routing Key 以 `rk_` 开头 |
| 7 | 消息体不超过 4M |

### 8.3 RocketMQ

| 资源 | 命名格式 | 示例 |
|------|----------|------|
| Topic | `业务线名_功能名` | `plat_goods_order` |
| Tag | `tag_业务细分类` 或 `tag_业务动作` | `tag_open` |
| ProducerGroup | `pg_业务线_服务名` | `pg_plat_goods` |
| ConsumerGroup | `cg_topic名_服务名` | `cg_plat_goods_order_sms_notice` |
| ACL 账号 | `u_业务线_服务名` | `u_plat_goods` |

- 每项目独立 ACL 账号
- 一类消息一个 Topic，消费者自行实现幂等
- 不同类型消息（普通/延时/事务/顺序）禁止同 Topic/ConsumerGroup
- ConsumerGroup 与 Topic 只能多对一或一对一
- 消息体不超过 4M（建议不超过 640KB）
- 业务线名称用直观公认名称（core/chl/clm/plat）

## 九、日志与监控设计

**9.1** 【强制】业务异常日志标准化，格式：`[应用名][模块名][方法名][关键业务参数] - 异常描述`。

**9.2** 【强制】正常日志记录关键业务节点，加入 ELK 监控。

**9.3** 【强制】日志级别规范：

| 级别 | 场景 |
|------|------|
| ERROR | 系统逻辑错误、影响业务的异常、需人工介入 |
| WARN | 用户输入错误、可恢复异常、性能预警 |
| INFO | 关键业务节点、系统启停、配置变更 |
| DEBUG | 开发调试，生产禁止输出 |

**9.4** 【推荐】关键业务操作日志包含完整链路信息，使用 TraceId 串联调用链。

## 十、错误码设计

**10.1** 【强制】错误码字符串 5 位：来源 + 四位编号。

| 前缀 | 含义 |
|------|------|
| `00000` | 全部正常 |
| `A` | 错误来源于用户 |
| `B` | 错误来源于当前系统 |
| `C` | 错误来源于第三方服务 |

**10.2** 【强制】错误码不能直接输出给用户。

**10.3** 【强制】错误码不体现版本号和等级，以追加方式兼容。

---

## 十一、安全设计

**11.1** 【强制】用户隐私数据传输和存储必须加密（身份证、手机号、银行卡、地址等）。

**11.2** 【强制】鉴权遵循最小权限原则。

**11.3** 【强制】表单提交前后端双重防重：前端 disable + 后端 Redis KEY 管控。

**11.4** 【推荐】大清单导出用单独服务，同一时间同一用户只能一个导出作业，耗时长的用异步。

---

## 十二、微服务设计规约

**12.1** 【强制】业务对象状态超过 3 个，必须用状态图表达。

**12.2** 【强制】调用链路涉及对象超过 3 个，使用时序图。

**12.3** 【强制】需求分析同时评估异常流程与业务边界。

**12.4** 【强制】新系统原则上不存在跨库（租户/用户）场景，跨库通过服务化方式实现。

**12.5** 【推荐】架构设计明确：系统边界、模块关系、演化原则、非功能性需求。

---

## 十三、版本管理

**13.1** 【强制】微服务禁止将代码合并至 PROD 分支。PROD 必须从 UAT 复制。

**13.2** 【强制】禁止未走流程进行生产变更。应用走 PUBLISH 流程，数据库和配置走 DC 流程。

**13.3** 【强制】多系统开发时建立关联 JIRA 号。

**13.4** 【强制】版本会议当日创建 Publish。

**13.5** 【强制】分支管理流程：

```
DEV → SIT → UAT → PROD (从 UAT 复制)
```

---

## 十四、流程管理

**14.1** 【强制】禁止 UAT 新增非生产额外代码。

**14.2** 【强制】禁止工作时间使用生产环境资源做非生产操作。

**14.3** 【强制】禁止白天业务期间抽数。

**14.4** 【强制】配置表变更需附带脚本走 JIRA 审批。

**14.5** 【强制】并发/线程/HTTP/大表操作等影响性能的代码，组长需走读审查。

**14.6** 批量操作管控：导入功能需评审；批量查询/算需科室负责人评审；取数和定时任务场景设计文档列明注意事项。
